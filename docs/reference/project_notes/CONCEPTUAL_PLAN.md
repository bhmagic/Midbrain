# Conceptual Plan for a Framework-Neutral Physical Agent Platform

The purpose of this work is to create a practical software platform that allows modern AI agents to operate physical robots without requiring every project to assemble a separate, tightly coupled stack of agent logic, hardware drivers, perception services, state management, and resource-control code.

The platform will initially use one established general-purpose agent framework as the high-level Agent Driver instead of trying to support every framework equally or creating a new agent framework. The current prototype uses OpenAI Agents SDK because model-directed tool selection and handoffs are useful for selecting among evolving Skills. The robotics runtime must nevertheless remain framework-neutral through a small Agent Adapter boundary. LangGraph, state machines, or conventional workflow code may be used inside individual Skills when explicit branching, checkpoints, recovery, human approval, or long-running execution state is useful.

The platform's central control-plane component is the **Resource Provider Manager**. It manages **Resource Providers**: persistent or reusable services that provide hardware access, data, computation, models, recording, visualization, or control. The Manager should discover providers, validate manifests, resolve dependencies, choose implementations, start and stop processes, manage `COLD`, `WARM`, and `HOT` residency, monitor health, arbitrate resources, apply fallback policy, and issue physical-control authority. A semantic capability is not a process; it is a function offered by one or more Resource Providers.

A **Skill** is finite, task-oriented orchestration. A Skill may request capabilities from multiple Resource Providers, read current state, obtain bounded authority, perform a task, return a structured result, and finish. Supporting Resource Providers may remain `WARM` or `HOT` for reuse. This distinction prevents hardware drivers, model servers, and high-cost perception pipelines from being repeatedly initialized for every agent action.

The **World State Fabric** is a first-class state-plane subsystem that is logically separate from the Manager. The Manager starts, configures, connects, monitors, and replaces the providers that contribute state. The Fabric accepts timestamped observations and should eventually combine them into a canonical, queryable representation of the robot, nearby humans, tracked objects, environment, task, transforms, and safety-relevant conditions.

Fusion should be multi-rate rather than tied to one global update frequency. Joint state, gripper state, controller status, contact, and human proximity may update at tens or hundreds of hertz. RGB-D tracking and workspace occupancy may update at intermediate rates. Semantic observations from vision-language models, object identity, and task interpretation may update more slowly or only on demand. Every field should retain provenance, timestamp, clock domain, confidence, validity, calibration revision, and freshness so delayed or stale information cannot silently replace newer state.

Large payloads must not be copied through the Fabric by default. RGB frames, depth maps, point clouds, audio blocks, video, and tensors should use shared memory or another large-data transport when producer and consumer are local. The Fabric distributes a **BufferRef** containing access metadata. Consumers validate slot generation and freshness before reading and reacquire a new reference when a ring-buffer slot has been recycled.

The Fabric should own a framework-neutral, timestamped transform graph. A ROS 2 Transform Resource Provider may bridge ROS 2 `/tf` and `/tf_static` into this graph and expose compatible queries back to ROS 2. ROS 2 remains a valuable provider ecosystem for drivers, navigation, simulation, action cancellation, and hardware integrations, but it should not define the platform's public Skill, Resource Provider, or world-state contract.

The high-level agent should reassess the situation through both periodic and event-driven triggers. Periodic reassessment recenters long-running tasks on current state. Event-driven reassessment should occur immediately for important changes such as target movement, target loss, unexpected gripper state, reduced perception confidence, a person entering the workspace, provider failure, user correction, cancellation, or an abort request. The Fabric should provide compact snapshots and change summaries; the agent decides whether to continue, observe again, ask the operator, replan, pause, invoke a bounded Skill, or stop.

Physical movement requires explicit software authority. The Manager should issue an expiring, fenced **Control Authority Lease** for each protected resource. A Skill may logically own a lease, but commands should normally flow through the hardware Resource Provider, which rejects missing, expired, or obsolete fencing generations. Lease release, expiry, revocation, provider failure, or Manager disconnection must trigger a predefined safe-relinquish behavior such as controlled deceleration, position hold, brake engagement, gravity compensation, bounded gripper-force hold, or transfer to a safety controller. Uncontrolled torque removal is not an acceptable default when an arm or payload may fall.

The runtime should support a bounded recovery Skill named **Abort & Retreat**. It is separate from an emergency stop. When requested, the system stops further task reasoning, rejects new manipulation actions, cancels or preempts the active Skill, examines trusted robot and gripper state, and follows a predefined recovery workflow. If no object is held, the robot may retract to an approved park pose. If an object is held and a verified safe placement is available, it may place, release, retract, and park. If state is uncertain, the robot should hold safely and request operator assistance. Completion should leave the task in an `ABORTED_LATCHED` state requiring deliberate operator confirmation before new motion.

Existing systems should be treated as reusable Resource Providers rather than permanent foundations. ROS 2 can provide mature drivers, transforms, navigation, simulation, and hardware integrations. Other projects may contribute typed streams, shared-memory transport, recording, replay, visualization, robot adapters, multimodal pipelines, or semantic state fusion. None should define the platform's public contracts by accident.

Portability belongs at the provider boundary. The Manager, Fabric, contracts, lifecycle semantics, world-state interfaces, and Agent Adapter should run across operating systems and CPU architectures wherever practical. High-performance Resource Providers may remain platform-specific and use CUDA, TensorRT, DirectML, DMA-BUF, Core ML, Metal, vendor NPUs, or vendor SDKs. A portable serialized or loopback transport should remain available as a fallback.

Distribution should distinguish source, binary, and installer packages. A source Resource Provider package may depend on a separately installed vendor SDK. A binary package may include redistributable runtimes and notices. An installer or bootstrapper should detect drivers, firmware, SDKs, runtime extensions, permissions, and hardware requirements before launch. Missing dependencies should fail during setup with a specific diagnostic rather than producing a partially working provider.

Development should remain incremental. The hardware-verified v0.2.0 prototype now validates a full Femto Bolt sensory Resource Provider, shared-memory BufferRefs for RGB, depth, IR, aligned depth, and XYZ point clouds, calibrated RGB-D/IMU geometry, synchronized bundles, Manager capability discovery, heartbeat expiry, Fabric stream discovery, and timestamp-nearest queries. The next milestone should add the native timestamped transform graph, followed by schema validation, process containment and restart policy, active stale-state invalidation, buffer leases, subscriptions, recording and replay, and Control Authority Leases tested first with a simulated arm.
